# Architecture Decision Log

Original concept: Michael D. Carter (BitsBeTrippin) · Built with Claude AI assistance · Apache-2.0

One entry per decision that would be expensive to reverse. Newest at the bottom. Format: context → decision → consequences.

## ADR-001 — Single Node.js runtime, browser dashboard on loopback
**Context.** Requirement for Windows/macOS, single user, npm-based install, local transcription, and a dashboard. Python offers stronger ML tooling; a desktop shell offers polish.
**Decision.** Node.js ≥ 22.13 (24 LTS recommended) + TypeScript for everything; React/Vite dashboard served by Fastify on `127.0.0.1`.
**Consequences.** One runtime to install; Whisper runs slower than native. Desktop packaging is deferred and can wrap the same backend later.

## ADR-002 — `node:sqlite` with forward-only SQL migrations; Drizzle adopted at Milestone 1
**Context.** better-sqlite3 needs prebuilt native binaries (Windows friction); `node:sqlite` is built in and RC-stable; Drizzle officially supports it.
**Decision.** Thin wrapper over `node:sqlite` now; Drizzle (`drizzle-orm/node-sqlite`) for typed schema/queries when content tables land; Drizzle-Kit generates SQL files that the existing runner applies. No down-migrations; pre-migration backup instead.
**Consequences.** Zero native compile step. If `node:sqlite` changes, one file (`server/src/db/index.ts`) changes.

## ADR-003 — Durable jobs as SQLite rows with an in-process worker
**Context.** Long operations (transcription, research) must survive restarts and be cancellable; Redis/BullMQ would add a service.
**Decision.** `jobs` table + polling worker; atomic claim; heartbeat; stale-heartbeat recovery; bounded retries; dedupe key.
**Consequences.** Simple and portable; throughput limited to one process (fine for a single user).

## ADR-004 — Secrets encrypted with AES-256-GCM under a local key file
**Context.** Keys must not appear in the browser, logs, exports, or git. OS keychains require native modules or platform tools.
**Decision.** Random 32-byte key at `<dataDir>/secret.key` (owner-only), per-secret IV, masked hints only in the API.
**Consequences.** Protects copied/exported databases; does not protect against same-user malware (same boundary as an unsigned app's keychain access). Keychain backing deferred.

## ADR-005 — Four provider interfaces, never one "AI" abstraction
**Context.** A text model cannot transcribe or browse; a local model must still be able to assess retrieved evidence.
**Decision.** `LanguageModelProvider`, `TranscriptionProvider`, `SearchProvider`, `SourceFetcher` are separate; stage routing picks an LLM per stage.
**Consequences.** Slightly more wiring; no accidental assumption that "the model will search."

## ADR-006 — Validation plan is a versioned artifact generated before research
**Context.** Criteria written after seeing evidence drift to fit it.
**Decision.** Plan generation is its own job; plans are immutable versions; every research run references one plan version; edits create a new version.
**Consequences.** Full auditability; some duplication of plan text across versions (acceptable).

## ADR-007 — Model memory is never evidence
**Context.** LLMs fabricate URLs and facts.
**Decision.** Only sources retrieved by `SearchProvider` + `SourceFetcher` can be cited; assessment output citations are validated against stored source ids. Search failure → *insufficient evidence*, never a verdict.
**Consequences.** Some predictions remain unresolved when the web is silent — by design.

## ADR-008 — Local Whisper via Transformers.js (ONNX) for MVP; whisper.cpp later
**Context.** Product owner chose pure-Node over a compiled binary to minimise install failures.
**Decision.** `@huggingface/transformers` with `onnx-community/whisper-*` models downloaded into the data directory; chunked with overlap. whisper.cpp remains a candidate engine behind the same interface.
**Consequences.** Slower on long videos; users can choose captions or OpenAI transcription instead.

## ADR-009 — Fetch adapters in 0.1; Vercel AI SDK for structured output from Milestone 1
**Context.** 0.1 only needs connection tests and model listing (which the SDK does not provide). Extraction/assessment need reliable JSON across three providers.
**Decision.** Keep `fetch` adapters for tests/listing; adopt the AI SDK behind `LanguageModelProvider.complete` after spike S-2 confirms behaviour with LM Studio.
**Consequences.** Two code paths inside one adapter; the app never depends on SDK types outside the adapter.

## ADR-010 — Apache License 2.0
**Context.** Open-source release with third-party components and possible contributions.
**Decision.** Apache-2.0 for original code; `NOTICE` carries concept attribution; `THIRD_PARTY_NOTICES.md` lists every non-original component with its license.
**Consequences.** Explicit patent grant and attribution mechanism; compatible with MIT/BSD dependencies; GPL binaries (ffmpeg) are invoked as separate processes, not linked.

## ADR-011 — Milestone order: transcript import first, media last
**Context.** Implementation context specifies analysis-first milestones; media processing carries the most platform risk.
**Decision.** 0.2 analysis core on imported transcripts → 0.3 research/verdicts → 0.4 local video → 0.5 YouTube → 1.0 evals/hardening.
**Consequences.** Value is demonstrable after 0.2 without ffmpeg or Whisper; transcript import is also the permanent fallback for YouTube failures.

## ADR-012 — Release 0.2 stays dependency-free; Drizzle and the AI SDK wait for a verified build
**Context.** Neither the build sandbox nor the linked machine could reach the npm registry during the 0.2 session, so spikes S-1 (Drizzle) and S-2 (AI SDK structured output) could not be executed. The 0.2 scope (transcript import → extraction → plans) needed a repository layer and structured model output now.
**Decision.** Implement 0.2 on the existing `node:sqlite` wrapper (with SAVEPOINT-based nested transactions) and the existing `fetch` adapters, using hand-written JSON Schemas for provider-side hints and Zod for app-side validation with a one-shot repair loop. Zero new runtime dependencies. Spikes S-1/S-2 move to the start of 0.3 and remain optional: adopt only if they reduce code.
**Consequences.** Two schema representations to keep in sync (Zod + JSON Schema, both in `analysis/schemas.ts`). Provider-side JSON enforcement differs by vendor (Anthropic forced tool-use, OpenAI/LM Studio `response_format`), so the app-side validator is the contract that matters.

## ADR-013 — Re-extraction preserves user-touched predictions
**Context.** Users will re-run extraction (better model, corrected transcript). Blindly replacing rows would destroy edits, plans, and review decisions.
**Decision.** A new extraction run deletes only *pending* predictions with no revisions and no plans, then skips candidates that closely match any surviving prediction (quote or normalized-statement similarity ≥ 0.8). Accepted, dismissed, edited, merged, or planned predictions are never touched by automation.
**Consequences.** A genuinely different re-phrasing may be treated as "already present"; the user can still split/merge by hand.

## ADR-014 — Built-in HTML extractor and fetch adapters for 0.3; Readability deferred
**Context.** Registry access was still unavailable, and 0.3 needs page text for evidence. Mozilla Readability + linkedom remain the intended upgrade.
**Decision.** Ship a dependency-free regex extractor (`research/htmlExtract.ts`: article/main preference, block-tag paragraphing, metadata for title/canonical/date/publisher) behind the `SourceFetcher` interface, with excerpt verification against the stored text. Search adapters (Brave, Tavily, SearXNG, Anthropic/OpenAI native) are plain `fetch`. Adopt Readability in 1.0 hardening if it measurably improves extraction on the fixture set.
**Consequences.** JS-rendered and paywalled pages yield thin text (recorded as coverage limitations). PDFs are recorded as unsupported sources in 0.3.

## ADR-015 — The verdict guard is code, not prompt
**Context.** Verdict rules (no results ≠ false, pending ≠ failed, announced ≠ implemented, anecdotes ≠ trend, one source ≠ corroboration) must hold regardless of model behaviour or user prompt overrides.
**Decision.** `research/verdictGuard.ts` applies rules G1–G7 deterministically after the model answers; it can only make a verdict more cautious, and every adjustment is stored in `guard_notes` and shown in the UI. Zero-evidence runs are assessed by rule without a model call. Excerpts must be found in the retrieved page text or they are discarded before assessment.
**Consequences.** A model that over-claims is visibly corrected rather than trusted; a model that under-claims is left alone. Users can override prompts without weakening the rules.

## ADR-016 — Raw-stream upload and a dynamically loaded, optional Whisper engine
**Context.** Release 0.4 needs file upload and on-device transcription. `@fastify/multipart` (busboy) would add a parsing dependency for one route, and `@huggingface/transformers` is large (ONNX Runtime binaries), downloads models, and could not be installed in the build sandbox. Users who only import transcripts or use OpenAI transcription should not pay for either.
**Decision.** (1) The upload route accepts the file as a raw `application/octet-stream` body, with the file name and metadata in request headers; the server streams it to a temp file while hashing and enforcing the size cap, validates it with ffprobe, then stores it under its content hash. No multipart parser. (2) `@huggingface/transformers` is an *optional* dependency imported dynamically inside `LocalWhisperProvider`; when it is absent the engine's readiness check reports exactly what to install, and the OpenAI engine remains available. Models are cached under `<data>/models/` and the first download is gated by the privacy switch. (3) ffmpeg stays a system dependency located via `PL_FFMPEG_PATH` → optional `ffmpeg-static` → PATH; child processes always receive argument arrays.
**Consequences.** Browser uploads are a single `fetch` with a `File` body (no form encoding overhead, streaming, resumable-friendly later). Multi-file or field-mixed uploads would need a different route. A missing `@huggingface/transformers` surfaces at transcription time rather than install time, so Setup exposes a *Check media tools* probe. Spike S-3 (real Whisper throughput on a 30-minute file, default model choice) moves to the first machine with a working `npm install`.

## ADR-017 — YouTube via a consent-installed, checksum-verified yt-dlp; captions before audio; Node as its JS runtime
**Context.** There is no official API that serves captions or audio for arbitrary public YouTube videos. yt-dlp is the practical tool, but it is a scraper that breaks when YouTube changes, it must not be fetched implicitly by npm (RT-05), and since late 2025 it needs an external JavaScript runtime for YouTube's challenges (Deno by default).
**Decision.** (1) yt-dlp is installed only when the user clicks Install in Setup (or the Library card): the official standalone binary for the platform is downloaded from the GitHub release and verified against the release's `SHA2-256SUMS` before it is moved into `<data>/tools/`; `PL_YTDLP_PATH` or a PATH copy are honoured instead. The same button updates it. (2) The import order is creator captions → auto-generated captions (policy and language configurable) → audio download (opt-out) → 0.4's `audio.extract`/`transcript.generate`; transcript import remains the fallback named in every failure message. (3) yt-dlp is pointed at the Node binary running the app (`--js-runtimes node:<execPath>`) so no second runtime is required. (4) yt-dlp only ever receives a canonical URL rebuilt from a validated 11-character id, via argument arrays; its JSON output is validated field by field. (5) `video.import` has `maxAttempts` 1: YouTube failures are classified and explained rather than retried blindly.
**Consequences.** Import quality depends on YouTube's caption availability; auto captions are flagged in the Library and can be replaced via Re-transcribe (audio + own engine). yt-dlp breakage is expected and surfaced as "update yt-dlp". Age-restricted and bot-checked videos stay unavailable (no cookie/PO-token support in MVP). The `--js-runtimes` flag and the whole live path are confirmed on the first machine with network (spike S-4); the fake-yt-dlp tests cover the app's own logic only.

## ADR-018 — Resilience policy for model calls, and retry as a new job
**Context.** Provider outages, rate limits, and slow local models were handled only by the job queue's blunt `maxAttempts`, which re-ran whole jobs (re-extracting every window) and retried invalid credentials pointlessly.
**Decision.** Every model call goes through `withResilience`: a per-try timeout (120 s, ref'd timer so a bare process cannot exit mid-call), up to three tries with quadratic backoff capped at 30 s for HTTP 408/429/5xx and network errors, `Retry-After` honoured, and an immediate failure carrying the provider's own message for 401/403. Job-level retry is explicit: `POST /api/jobs/:id/retry` creates a *new* job with the same payload rather than reviving the old row, so history stays intact and dedupe keys still apply.
**Consequences.** A flaky provider costs at most three short waits per window instead of a whole job re-run; an invalid key fails in seconds with an actionable message. Timeouts are not yet user-configurable (a Setup field is queued for 1.0 if real runs show the need).

## ADR-019 — Labelled synthetic fixtures + Promptfoo, rendering the app's built prompts
**Context.** Cross-provider quality checks must exercise exactly what the app sends, and must be re-runnable as prompts evolve.
**Decision.** Evals render prompts by importing the built `server/dist` templates and windowing code (no copied prompt text), score against the same `expected.json` files the unit tests use, and treat modality drift and invented deadlines as hard failures. Fixtures stay synthetic and clearly labelled; a 30-minute fixture (B1) is generated with planted, human-reviewed statements so window boundaries and repeats are exercised deterministically.
**Consequences.** `npm run build` is a prerequisite for `npm run eval`; Promptfoo is fetched with `npx` rather than added as a dependency. Threshold values are recorded only once the suite has run on real providers (1.0).

## ADR-020 — 1.0.0 is gated on a verified run, so the feature-complete build ships as 1.0.0-rc.1
**Context.** All MVP requirements have implementations and tests, but the build environments available so far could not install the real dependencies (npm registry blocked in the sandbox; the linked machine's workspace could not mount folders). Calling that "1.0.0" would assert a verification that has not happened.
**Decision.** Tag the feature-complete build `1.0.0-rc.1`. `1.0.0` is cut only after `docs/FIRST_RUN.md` has been completed on at least one Windows and one macOS machine, spikes S-3/S-4 are answered, and eval scores are recorded in `docs/VERIFICATION.md`. Fixes found during that run are rc.2, rc.3… — no new features.
**Consequences.** The version string tells users exactly what they are getting. `npm run doctor` and the runbook exist so the verification loop is cheap for whoever runs it.

## ADR-021 — Sports picks are settled, not researched
**Context.** Product-owner rule (2026-09-12): for game-related videos (NFL, NBA, NHL, MLB, soccer, …) the prediction scope is the win, the spread if stated, and whether it was met after the game date; deep research is wasted on them. Sports results are linear (win/loss, occasionally a tie/push).
**Decision.** A prediction extracted with a `sports_pick` becomes `kind = sports_pick`. Its deadline is the game date, its single component is the pick, its validation plan is generated by code (settlement rules + score look-up queries, version `plan.sports.v1`) with no model call, its research budget is capped at three searches and three sources, and its assessment uses a settlement template whose labels map hit → supported, miss → contradicted, push/draw → partially supported, no final score → insufficient. The general path is untouched; a season-long or futures claim in the same video remains a general prediction.
**Consequences.** Picks cost one evidence-extraction call per fetched page plus one settlement call; criteria cannot drift because they are code. Game dates are never guessed: a pick without a stated date has an unknown deadline until edited. Player props and parlays are out of scope (they would need their own settlement rules).

## ADR-022 — Validate scores is a chained one-click action with a trusted-source filter
**Context.** Owner request (1.3): no plan review or evidence work for sports picks beyond the final score; a dedicated button; a Sports Mode switch; spreads optional.
**Decision.** `POST /api/predictions/:id/validate-score` reuses the existing job chain (plan.generate → research.run → assessment.run) rather than a new pipeline, because the sports plan is already code-generated and the assessment template already settles; the route only adds the pre-checks (sports pick, game date reached, search available) and skips the review stop. Research for picks ranks trusted score hosts first and fetches only those when any exist, recording which case applied in coverage notes. Sports Mode is a prompt steer plus the spread toggle; picks are still detected with it off.
**Consequences.** One button, one job chain, same history/versioning/guard rules. The trusted-host list is a constant to edit (`analysis/sports.ts`); an untrusted-only result set is still settled but flagged for verification.

## ADR-023 — A missing game date is looked up from the schedule, never inferred
**Context.** Real run (1.3.0, owner): picks videos rarely say the date — "Week 1", "Sunday night" — so every pick had an unknown deadline and Validate scores refused. The owner asked that Validate scores find the date itself ("crawl the web or parse the schedule").
**Decision.** A dedicated job, `sports.resolve_date`, runs before the settlement chain when the deadline is unknown. It is search-driven (same provider, cache and SSRF-guarded fetcher as research; trusted hosts first) and parser-first: a deterministic parser accepts a date only when both team names sit on the same line as the date or in the rows under a date header, inside a window around the video date, and refuses ties. The model is a fallback reader of the same fetched text, told to report a stated date or null, and its answer is accepted only at medium/high confidence. The extraction model is explicitly forbidden from turning "Week 1" into a date; it records the phrase as `eventHint` for the query instead. The result is recorded with its provenance (`deadlineBasis: lookup`, source URL, a revision) so a wrong look-up is visible and editable.
**Consequences (superseded by ADR-024 for the job itself; the parser and provenance rules stand).** "Deadline unknown" on a pick is now a rare outcome (no schedule page found, or ambiguous). The date is a claim from a web page, not from the transcript, and the UI says so. Cost: at most two searches, three page fetches and (rarely) one small model call per pick. Non-English or non-Western date formats are not parsed; the model fallback covers them when a page is found.

## ADR-024 — One game record per matchup; picks settle by rule against it
**Context.** Owner (2026-09-14, after the 1.3.1 run): sports validation should confirm only *winner, score, date*. Four picks that all say "Bills vs Chiefs" should reconcile against the single fact that the Bills and Chiefs played on a given day with a given final, then each pick is matched to it. Sports results are linear and nobody publishes false finals, so the general evidence/assessment machinery is overkill.
**Decision.** A `games` table holds one record per real game (matchup key = sport + both nicknames). `sports.resolve_game` looks the game up once — stored record first, then two searches with a deterministic score reader over snippets and trusted pages, the model only as a fallback reader whose excerpt must be verbatim — and settles every pick on that matchup by code (`settlePick`). Settlement writes the same run/evidence/assessment rows the general path uses, with provider `app`, so history, export and the dashboard are unchanged; it never calls the model to judge. A missing score leaves the picks pending; a postponed game likewise. Re-validate forces a fresh look-up.
**Consequences.** A picks video costs one look-up per distinct game, not per pick, and identical matchups across videos share the record. The 1.3.1 date-only job is folded in (its parser resolves the date from the same text). The model-driven `sports_assessment` template is no longer on the pick path; it remains for anyone who runs Research on a pick by hand. Player props, parlays and totals with quarter/half scopes remain out of scope.

## ADR-025 — Prediction markets enter as a read-only provider behind an interface; trading is out of scope
**Context.** Owner (2026-09-15): pair the ledger's extracted claims and settled results with live market odds and liquidity (Polymarket first), to weight predictions across channels and mark confidence on a market side. Polymarket's market data is public and unauthenticated; trading requires a wallet/API key and is geo-restricted.
**Decision.** Add a `MarketProvider` interface alongside the existing provider interfaces and ship Polymarket as its first adapter, read-only, with no settings or storage in 1.5. Storage (markets, snapshots, prediction↔market links), proposal-only matching with user acceptance, creator track records and edge/confidence signals follow in 1.6–1.8 as laid out in docs/PREDICTION_MARKETS.md. Any order placement, if ever, is a separate release with its own ADR, consent screen and key store; a paper-trading ledger is the intended intermediate step.
**Consequences.** The app can show what a market says without any account. The hard problem — deciding that a spoken claim and a market's resolution rules mean the same thing — is treated as a matching problem with human acceptance, not as an API problem. Sports picks map deterministically (teams + game date → the event's moneyline/spread/total market); general predictions get scored proposals.

## ADR-026 — Market links are proposals with human acceptance; only exact sports matchups auto-link
**Context.** 1.6 stores markets and links them to predictions. Venue search is loose and a market's resolution rules can differ from a spoken claim in scope, threshold, geography or deadline; a wrong link would silently poison every downstream signal (1.7).
**Decision.** `market.match` writes *proposals* with a deterministic score and a rationale naming what matched; for general predictions the assessment-stage model may add a relation label (same / narrower / broader / different) but cannot accept a link. The user accepts or rejects in the Markets tab, and an accepted/rejected status is never overwritten by a later run. The single exception is a sports pick whose two teams, game date (±2 days of the market end) and pick type all line up with a game market — that is a deterministic identity, and Setup → Markets can turn even that off. Snapshots are appended, never overwritten, so a link can always be read against the price at the time.
**Consequences.** Signals in 1.7 are computed only over accepted links. The matcher's false positives cost a click, not a bad number. Cost per match: two venue searches and at most one small model call.

## ADR-027 — Signals are realized-edge-based, shrunk, gated, and computed on read
**Context.** 1.7 needs a number for "how much should this creator's claim move me off the market price" that cannot be gamed by calling favourites, that degrades gracefully with thin records, and that never manufactures confidence from one video.
**Decision.** The creator statistic is *realized edge*: over settled predictions with an accepted market link and a venue price from when the claim was made, the mean of (outcome − price) — the per-dollar return of taking the creator's side at the market's price. For an open claim the creator's realized edge, shrunk by n/(n+k) toward zero, is added to the current market price; several creators on one market side combine by settled-count weight, one contribution per video. A label (strong / moderate / lean / none) is a set of gates on record size, edge size, liquidity and deadline consistency, all editable in Setup, with every failed gate reported. Nothing is stored: signals are a query over predictions, assessments, links and snapshots, so a corrected verdict or a rejected link changes them immediately. Price-at-made comes from venue history when available, else the link-time snapshot, and the source is shown.
**Consequences.** A thin record produces "no signal", by design. Hit rate is displayed but never drives a label. Correlated creators (same channel across videos) are one creator; correlated *channels* are not detected yet. The math is in pure functions with fixture tests; the service is a join.

## ADR-028 — Consensus is shown as a split, alerts are local and deduped, and the second venue proves the interface
**Context.** 1.8 adds many-channel input. Averaging disagreeing creators into one number hides the information the owner asked for ("the range of potential bets"); a watch that repeats itself every six hours is noise; a second venue is the test that `MarketProvider` is real.
**Decision.** Propositions are grouped (by linked market, else by statement overlap) and each side keeps its endorsements and weight share; no single consensus number is produced for a split proposition. Watch rules write one alert per rule/subject/day into a local table and never leave the machine. Manifold is added as the second adapter with play-money units carried in tags rather than converted; venue selection lives in Setup. Paper trading is not built: it changes the schema (positions, marks, P&L) and is the natural place to test whether signals mean anything, so it needs the product owner's yes.
**Consequences.** A user sees who says what and how much record backs it, and gets told when the market moves against that. Manifold liquidity in mana will trip the dollar-denominated signal gates unless the gate is lowered for that venue — noted in Setup. Correlated channels (the same person on two channels) are still two creators.

## ADR-029 — Paper trading is the scoreboard for signals; order placement remains out of scope
**Context.** 1.7 produces labelled edges; 1.8 adds consensus and alerts. Without a scoreboard nobody can tell whether the labels mean anything, and the honest scoreboard is "what would following them have returned at the market's price".
**Decision.** Add a hypothetical position ledger: positions are opened at the current snapshot price (by hand from a Signals row, or automatically on labelled signals when opted in), marked at every snapshot, and closed at 1/0 on venue resolution. Sizing is fixed or fractional Kelly on the signal's edge with a hard cap. The book reports P&L and, over resolved positions, the estimate Brier beside the market Brier. No venue account, wallet, key or order endpoint is touched; the paper ledger lives in SQLite beside everything else and can be reset. Real trading, if ever, remains a separate release with its own ADR, consent screen and key store.
**Consequences.** The signal pipeline now has a falsifiable output. Kelly sizing assumes the estimate is calibrated, which is exactly what the book tests, so quarter-Kelly and a bankroll cap are the defaults. Manifold positions are in mana; the book adds them to dollars without conversion, so a mixed book should be read per venue (a later refinement).

## ADR-030 — A Polymarket US execution module supersedes the "never trade" rule, behind release gates; 1.10 ships reads only
**Context.** ADR-025 and ADR-029 excluded order placement. The product owner's September 2026 requirements pack (`02-Development-Requirements.md`, releases 1.10 → 2.0) asks for evidence-linked execution on **Polymarket US retail** — a CFTC-regulated USD exchange with its own hosts, key-based API and rules — with paper, manual-live and bounded automatic-live modes, each behind its own acceptance gate. The international Polymarket venue stays research-only (its trading is geo-restricted for US users); Manifold is play money.
**Decision.** The "never" becomes "only for an explicitly enabled Polymarket US module, and only after its release gate is met". Concretely: (1) `polymarket_us` is a **distinct** `MarketProvider` — separate hosts, ids, rules text and constraints; existing `polymarket`/`manifold` rows are never converted and can never enter the US execution path. (2) A **separate `TradingAdapter`** (`providers/trading/`) is the only code allowed to hold a venue credential; `MarketProvider` stays read-only. (3) In 1.10 the adapter exposes account reads and a targeted cancel — **no create/preview/modify method exists**, so submission is impossible by construction, not by configuration. (4) The trading mode lives in its own `trading_policy` row (default `paper`, live authorization absent) that the generic settings save cannot touch; live modes are refused with the list of unmet gates; live-control routes answer `501 feature_disabled`. (5) Every default test uses a fake adapter; the single live check is an opt-in, owner-run, read-only script. (6) Later gates: 1.11 verified contracts, 1.12 immutable forecasts/decisions and reservations, 1.13 manual-live with reconciliation, 1.14 automation, 2.0 verification — each adds code only when the previous gate passed.
**Consequences.** The 1.5–1.9 read-only design stays intact and documented; docs/PREDICTION_MARKETS.md's ground rule is amended to point here. A user can connect an account today and read it; nothing they can click or POST places an order. The cost is a second adapter family, a vault boundary inside the secret store and an audit table — all of which the later releases need anyway.

## ADR-031 — Polymarket US integration questions (spec §14) answered with evidence, 2026-09-16
**Context.** The requirements pack lists six integration questions that must be answered from official sources or recorded as unresolved, never guessed. Sources: docs.polymarket.us (API reference pages fetched 2026-09-16), the `polymarket-us` TypeScript SDK source and published dist (npm `latest` = **0.1.1**, MIT, verified through jsdelivr's registry mirror — the npm registry was not reachable from the build sandbox), and live calls to the **public** gateway (no credentials).
**Answers.**
1. **Stable account identity** — *not exposed.* `GET /v1/account/balances` returns balances only; `GET /v1/portfolio/positions` is keyed by market slug; the RFQ overview states "the Retail API derives the participant and account from the API key; clients do not send an account", and `GET /v1/rfqs/user-id` returns a *pseudonymous RFQ user id* whose stability across key rotation is undocumented. **Decision:** bindings are local (app id + SHA-256 fingerprint of the credential's Ed25519 public key), continuity across rotation is `unverified` (new binding, reconcile required) unless the owner asserts it (`user_asserted`, still reconcile required). **Owner check pending:** whether `/v1/rfqs/user-id` returns the same value for two keys of one account; if it does, a later release may record it as `identity_kind = venue_verified`.
2. **Idempotency / correlation ids** — *none.* `CreateOrderRequest` has no client order id or idempotency field; the SDK sends the body verbatim. A lost POST response can only be resolved from `GET /v1/orders/open`, `GET /v1/order/{id}`, `GET /v1/portfolio/activities` and the private WebSocket order stream. **Decision for 1.13:** `submission_unknown` + reconciliation by snapshot; a local key is never treated as venue-honoured.
3. **Retail test environment** — *none documented.* The "preprod" environment belongs to the institutional Trader Guide (JWT auth, different hosts). **Decision:** deterministic fake adapter for every automated test; owner-run production checks stay explicit and capped; 1.10's only live check is read-only.
4. **Market fields** — verified live: `category`, `startDate`, `endDate`, `gameStartTime` (deprecated but populated), `status` (`MARKET_STATUS_OPEN|RESOLVED|…`, not in the OpenAPI schema), `orderPriceMinTickSize`, `minimumTradeQty` (contracts; `0.01` = partial contracts), `feeCoefficient` (0.06 today), `sportsMarketTypeV2`, `line`, `marketSides[]` with durable `id` and `long` (the YES instrument) — and events carry `startTime`, `gameId`, `teams[]`. The deprecated `outcomes` array's **order varies** (`["No","Yes"]` vs `["Chargers","Titans"]`) and is never used for orientation. No rule-revision/version field exists: the rules hash (1.11) is computed over `description`. A market fetched by slug carries no event reference; search/league listings do.
5. **NO intent and price** — `price.value` is always the YES price; buying NO at $X is `ORDER_INTENT_BUY_SHORT` with `price.value = 1 − X` (docs "Understanding Price with Order Intent"; example USC/Iowa). The SDK's `orders.create` posts the params unchanged (verified in `src/resources/orders.ts`), so the conversion is the app's, applied exactly once (1.13). Balances arrive as JSON **numbers** (`format: decimal`); positions and prices as decimal strings — the adapter records which (`precisionSource`).
6. **Fees, restrictions, cancellations, settlement** — fee `Θ × C × p × (1 − p)`, taker Θ 0.06 with a published change to **0.0695 effective 2026-09-16 23:59 ET** and per-market `feeCoefficient`; never frozen in code, persisted per decision (1.12+). Cancel is `POST /v1/order/{id}/cancel` with `{ marketSlug }`; batched cancels echo ids without confirming. Settlement: `GET /v1/markets/{slug}/settlement` and `ACTIVITY_TYPE_POSITION_RESOLUTION` activities. Account restrictions surface as HTTP 401/403 (mapped to `unauthorized`/`forbidden`); the exact body of a *restricted* account response is **unverified** until the owner check runs. Rate limit 20 req/s per key and per IP.
**Consequences.** Every gap above is a blocked feature or a documented smaller scope, not an invented field. The SDK is pinned exactly (`polymarket-us@0.1.1`) and used only as the signed transport, because its `MarketDetail`/`MarketBook`/`UserPosition` types are narrower than the API (no tick/min-qty/sides/fee; `book` wraps in `marketData`; no `*Decimal` position fields).

## ADR-032 — A contract is "known" only through a computed rule checklist; similarity, acceptance and user review never authorize execution (1.11)
**Context.** 1.6–1.10 link predictions to markets with a similarity score and a human accept. That is right for research (a wrong link costs a click) and wrong for execution (a wrong link costs money on a contract that settles on different rules). The requirements pack (MAT-01…06, M01–M09) asks for exact event identity, rules text, timeframe, threshold/line, units and side, with missing dates, line mismatches and changed rules blocking outright — and for the prospective evidence gathered for a forecast to stay separate from the retrospective verdict (SRC-04).
**Decision.** (1) A **contract verification** is a versioned row computed by a pure function (`analysis/contractVerification.ts`) over the stored prediction, the stored game (when any) and the venue market's rules text and constraints. Every field is `verified`, `incompatible`, `missing` or `not_applicable` with what the claim requires and what the contract states; the status is derived — `incompatible` if any field contradicts, `incomplete` if any required field is missing, `research_only` for any venue other than Polymarket US, `verified_equivalent` only when every required field is verified — and there is **no route that sets it** (`PUT/PATCH …/verification-status` → 405). (2) The link's `score`, `relation` and `accepted` status are inputs to discovery and research; `executableLinks()` returns only `verified_equivalent` links, and accepted links from earlier releases start `unverified`. (3) A documented user fact (`{value, source}`) can fill a *missing* field that is not a hard gate; it cannot flip an `incompatible` field and cannot touch venue, market open, rules hash, side, teams, question or settlement conditions. (4) The side is mapped from the venue's durable side ids and the claim's team or negation semantics — never from the outcomes array's order, a label string or the slug. (5) Every verification stores the rules hash (sha256 of the venue's rules text), the claim's quote hash and revision; revalidation compares those plus market status, dates and side ids and marks the version **stale** with reasons rather than editing it; editing, merging or splitting a prediction invalidates its verifications immediately. (6) The cutoff is the earliest of game start, event start, trading close and the claim's observation cutoff; an unknown cutoff is recorded as unknown so that later automation must block. (7) A **sports pick with no stated period is the full game including overtime** (the ordinary meaning of a moneyline/spread/total); a US moneyline contract silent on overtime is treated as full game, a spread or total contract silent on overtime is `missing` on that field. This convention is recorded here because it is a judgement, not a fact in the transcript. (8) Research runs carry a `purpose`: a `forecast` run stores evidence with a cutoff instant and never chains an assessment; `assessment.run` refuses it. Forecast evidence therefore cannot become a verdict by accident, and verdict evidence gathered after the fact cannot masquerade as forecast-time knowledge — the dossier's `asOf` replay counts a source from its `first_seen_at`, and a publication date is only a labelled, opt-in assumption. (9) Source provenance is immutable: `first_seen_at` never moves, text and hashes are never rewritten, withdrawal and missing pages are status changes, and re-extraction produces a new analysis version while leaving accepted, edited or linked predictions byte-identical.
**Consequences.** The exit demo passes on structure, not on vibes: an exact contract verifies with every field shown, and a convincing near-match (same teams next week, −3.5 vs −7.5, first half vs full game, touch vs close, `>` vs `>=`) is rejected with the differing field named. The cost is that many real contracts will be `incomplete` on first contact — a missing start time, an unparsed rules sentence — and will need either better parsing or a documented fact; that is the intended failure direction. Nothing in 1.11 consumes a verification: forecasts (1.12) and previews (1.13) will require `verified_equivalent` and a non-stale version.

## ADR-033 — Forecasts are frozen inputs, decisions are pure and reserve before they act, and paper execution shares the live path's functions (1.12)
**Context.** The requirements pack asks for reproducible forecasts (FOR-01…07), a pure trade/no-trade decision with atomic reservations (RSK-01…07), and an execution-aware paper mode that uses the same contract verification, forecast, decision and risk functions live execution will (FOR-08). The 1.9 paper book opens at a snapshot price with no fees, depth or IOC semantics — useful as a scoreboard, unusable as a rehearsal.
**Decision.** (1) The §7 estimator is implemented as a versioned pure function (`baseline-edge-v1`) and nothing else may produce a probability: consensus share, extraction confidence and match quality are displayed, never traded on; research evidence qualifies, contradicts or blocks a contribution and gets no numerical multiplier. (2) A forecast is an **immutable snapshot** (update trigger) of everything that went in — the prior, every contribution with its history, the input versions as of the instant, exclusions with reasons — plus a sha256 hash; a replay at T after later data is byte-identical, because every input is filtered by the instant the app learned it (first-seen, resolution observed, verification created, revision created). (3) The trading cohort is stricter than the 1.7 creator record: an observation needs a link that was verified equivalent, a chosen-side price at or before the claim's *earliest possible* instant (a date-only claim is midnight UTC; the 1.7 noon price is therefore excluded — a deliberate loss of data, not a bug), and an official venue resolution; research verdicts are never outcomes; voids are reported and excluded. (4) The decision is a pure function of explicit inputs and a supplied clock; it evaluates **every** gate and returns each with a stable reason code, sizes with fixed-point decimals to the venue's increments, floors YES and ceils the NO complement to the tick, and rechecks cost and edge after rounding. (5) Exposure is recomputed and the reservation inserted **inside the same SQLite transaction** as the decision, and the contract's single entry opportunity is consumed there too; reservations carry the daily bucket they were made in, filled commitment is consumed for good, and a timezone or limit change is hashed, audited, disarms, and never touches consumed allowances. (6) Paper execution is a separate USD bankroll (`us-ioc-v1`) filled from timestamped side-specific depth at the limit with per-fill fees and IOC cancellation of the remainder — never a midpoint, never a top-up — and settled only from the venue's published resolution; the legacy book keeps its method label and reports per-unit subtotals so mana is never summed into dollars. (7) A strategy qualification record is produced only by an evaluation over production decisions that passes the gate (≥ 100 settled events, Brier ≤ market baseline, ≥ 20 usable observations per weighted creator, ≥ 2 independent clusters); fixture-sourced records are stored as such and can never qualify; the trading gate reads only production records. (8) Decision-lineage tables carry no cascading foreign keys to source content: deleting a video never deletes a decision's rationale, because the decision keeps its immutable input snapshot.
**Consequences.** Paper decisions are now a rehearsal of the live path rather than a different game, and every one of them — skipped ones included — is inspectable down to the gate. The price is honesty about data: most creators will have `no usable history` until verified, resolved, pre-claim-priced observations accumulate, so early forecasts will read `insufficient_data` and the paper book will stay quiet; that is the intended failure direction. Cross-process dispatch locking (OPS-03), venue acknowledgement of reservations (RSK-06 live), previews, intents beyond paper and `submission_unknown` handling are 1.13 work and are absent, not stubbed.

## ADR-034 — One send, no local idempotency claim: intents commit a marker before the POST, ambiguity becomes a held state the owner resolves, and only official activity settles (1.13)
**Context.** The Polymarket US retail API (verified 2026-09-16 against docs.polymarket.us and `polymarket-us@0.1.1`) has no client order id and no idempotency key; `POST /v1/orders` returns an exchange id on acceptance and nothing that proves a lost response was or was not applied; trade activities carry no order id; the private stream is the only push channel and can drop. The pack forbids blind resends, invented identity, guessed attribution and "exactly-once" claims based on a local key (EXE-03/04/05).
**Decision.** (1) **Preview → confirm is the only order path.** A preview is bound to the decision's immutable rationale hash, re-decided with a fresh book and account, valid for 60 s, and consumed by the first confirm; a confirm carries only the preview id and the hash. (2) **Two commits before the wire.** T1 reserves (intent + reservation + the contract's single opportunity, one transaction); T2 writes the `submitting` marker only if the policy is still manual-live and authorized, this process holds the dispatch lease and no hold is open — so a disarm, a lost lease or a hold are serialized against the send by SQLite, not by luck. (3) **Exactly one POST, classified, never retried.** 400/401/403/404/429 mean "not created" and release; anything else — timeout, reset, 5xx, a 2xx without an id, a crash after the marker — means "may exist": the intent becomes `submission_unknown`, the reservation is kept, the account's dispatch is paused, a hold is opened. The generic job queue has no execution kind, so nothing can resend by accident. (4) **Reconciliation proposes, the owner decides.** Candidate venue orders (same market/side/quantity/price, created near the marker) are listed on the hold and never linked; the owner either links one (its fills then settle the reservation once) or declares the venue shows no order (release). Absence from a query is not permission to resend. (5) **Executions are facts, states are monotonic.** An execution is unique by execution id and by trade id across every source, rows are append-only, order states only advance, cumulative quantities never shrink, a cancel of the remainder keeps the fills, and the reservation settles once on the terminal state from the venue's average price and fees. (6) **External is external.** Orders and trades the app did not place are stored and displayed with no rationale; a trade activity is attributed to one of our orders only when exactly one order of ours on that market can still absorb it. (7) **Only official settlement settles.** A `positionResolution` activity produces market- and intent-level events keyed by activity id; corrections are new events; a quote at .99, a market status or a research verdict settles nothing live. (8) **One dispatcher per data directory** through a leased row, renewed by heartbeat, re-checked in T2.
**Consequences.** The app can honestly say what it did (one send) and what it knows (acknowledged / filled / unknown / rejected) without pretending to know what it cannot; the cost is that an ambiguous outcome halts new orders until a human looks — the intended failure direction for real money. Fills can lag the venue by one reconciliation cycle when the stream drops; positions can show a discrepancy that is simply a manual sale on the website until the owner notes it. Automation (arming by policy hash, scheduler, emergency stop) arrived in 1.14 (ADR-035) and builds on these same commits; a manual-live decision still never sends without a human confirmation.

## ADR-035 — Automation is armed against a reviewed policy hash and a production qualification, runs on its own scheduler, and every change or fault returns it to disarmed in one statement (1.14)
**Context.** 1.13 made a single human-confirmed send safe (ADR-034). 1.14 (AUTO-01…05, DASH-01…05, OPS) asks the app to place bounded orders *without* a confirmation per order. The pack forbids pyramiding, repeated IOC top-ups and catch-up entries after cutoff; requires that reimports and policy edits cannot reset a consumed opportunity; requires stop to serialize against the final dispatch and to cancel only app-owned unfilled orders; requires restart/restore/change to return disarmed; forbids the generic retry path from touching submissions; and states that qualification fixtures are not strategy evidence.
**Decision.** (1) **Arming is its own route and its own sentence.** `POST /api/trading/arm` needs `AUTO_LIVE_ACKNOWLEDGEMENT` verbatim, the *current* policy hash (which now covers the limits, the budget timezone **and** the scheduler budgets), a category and a strategy version; the pair must hold a `production`-scope qualification for the current estimator, at least 20 settled paper positions must exist, and every manual-live gate plus `not_paused` and `breaker_closed` must pass. A bare `mode: 'auto_live'` on the policy route always fails. The authorization records the exact hash, version and category. (2) **One scheduler, not a job.** `AutoTraderService` ticks on its own timer in the server process, enqueues only discovery (`market.match`), and places orders through the 1.13 `preview → submit` functions; `liveEnabled()` is re-checked immediately before each send. Long jobs never delay a tick, a cancel or the stop; nothing in the scheduler retries a send. (3) **Opportunity keys are consumed forever** by the first `reserved` entry and returned only when the venue refused and nothing was created; `cutoff_passed`, `opportunity_consumed`, `intent_open` and `reevaluate_window` are recorded per candidate so the ledger explains every non-order. (4) **Any change disarms in one statement**: limit or budget edit (new hash), credential change, restart (`startupCheck`), backup restore (portable scrub clears `authorized_*`), an unknown submission, a reconciliation discrepancy, or the circuit breaker opening — each is a single UPDATE that clears the mode and the authorization and raises one `disarmed` alert; re-arming always requires re-reviewing the hash. (5) **Stop is one statement followed by targeted cancels.** `emergencyStop` disarms **and** pauses in one UPDATE (which contends with T2's conditional marker UPDATE on the same row, so a send either sees the stop before its marker or proceeds to acknowledgement and is then cancelled), audits, alerts, and cancels every app-owned non-terminal `venue_orders` row through `cancelIntent`. Orders the app did not place are untouched; `POST /api/trading/cancel-all` with `CANCEL_ALL_ACKNOWLEDGEMENT` is the only account-wide cancel. (6) **A circuit breaker on adapter faults** (consecutive failures other than 400/404, threshold and cooldown in the hashed budgets) opens, disarms and raises exactly one alert; it closes only after a success past the cooldown. (7) **Alerts are incident-keyed** (one row per incident, count and last-seen updated) so a flapping stream produces one open alert, not a page of them. (8) **The ledger is derived, not written**: a read-only join of decisions, intents, venue orders, paper positions and verifications; external orders and trades appear only from venue data with no rationale; marks older than 15 min are flagged stale; exports and backups carry no secret and no authorized hash. (9) **Fixtures never qualify.** `qualifiedCategories()` reads production-scope qualifications only; the tests that arm do so through a labelled SQL shortcut that inserts a production row into a throwaway directory.
**Consequences.** Automation cannot be armed on a real directory until a real production evaluation qualifies a (strategy version, category) pair and 20 paper positions have settled — the dashboard says so instead of offering a button. The owner reviews one hash and every drift from it (even a 1 ms budget edit) costs a re-arm; that friction is intended. A stop can race a send that already reached the wire; the outcome is an acknowledged order that is cancelled immediately, and any fills it caught are kept and shown (never hidden). The scheduler adds a second loop to the process (with the execution loop of 1.13); both are bounded by the same lease so two processes on one directory still dispatch at most once. What 1.14 does **not** do: it does not equate a fixture run, a green test or a 2xx with a verified fill; the 1.13 capped smoke test and the 1.14 owner acceptance (SETUP §4.15) remain pending owner execution.

## ADR-036 — 2.0 ships as a release candidate: review findings are fixed with regressions, drills and reports are executable, and the owner-only evidence is listed instead of assumed (2.0.0-rc.1)
**Context.** The pack's 2.0 exit is evidence, not features: an upgrade/restore drill on authentic data, qualification evidence, Windows verification on real content, scoped owner-run live checks and no open P0/P1. A code review of the 1.13/1.14 execution path (docs/VERIFICATION.md, RV-01…RV-14) found two P1 defects (the armed strategy/category scope was recorded but never enforced; a second process's crash recovery could corrupt an in-flight submission) and one defect that would have stopped every real decision (`now` captured before the book fetch → negative freshness → `BOOK_STALE`). None of the owner-only evidence exists yet, and no production qualification exists anywhere.
**Decision.** (1) **Fix everything the review found, on the production path, each with a regression test** (`services/review20.test.ts`), rather than documenting workarounds: the armed scope becomes a decision gate (`authorized_scope`); crash recovery runs only in the lease holder and every commit point re-checks the row it moves (T2 `changes === 1`, T3 guarded, `finishUnsent` conditional); the decision instant is taken after its inputs with a 2 s skew tolerance; a 429 is ambiguous; an unknown submission can be linked only to an order on the same contract and side; the newest production evaluation decides qualification; settlement P&L is cross-checked against the venue's realized amount and contested on contradiction; external sells are signed by action × side; the stop waits for the in-flight POST; pre-migration backups are scrubbed; the loss stop uses the budget timezone; the FOR-06 threshold counts distinct events. (2) **Drills are code, not instructions.** The upgrade rehearsal (`services/upgrade.ts`, `npm run upgrade:rehearse`) migrates a copy and proves byte-level preservation of every legacy row, isolation of US records and a disarmed policy; its fixture is an **authentic 1.9.0 database produced by the released 1.9.0 code**, merged from that version's own test runs and shipped as a gzipped SQL dump with no ciphertext. The key-file protection is applied and *verified by parsing the platform's ACL* (`security/keyFileAcl.ts`), never inferred from a POSIX mode. (3) **Reports say "pending".** The soak report judges the O07 thresholds and the qualification report the FOR-06 gate; both are derived read-only, both label a synthetic run as a harness rehearsal, and "insufficient data" is printed as an unmet gate with the number of events still needed — never rounded up, never written as a production record. (4) **The version is `2.0.0-rc.1`** and stays an RC until the owner-only evidence is recorded in VERIFICATION.md: Windows run on real content, the capped smoke test, the real seven-day soak, a production qualification, the rehearsal on the real 1.9 data, the first real settlement. (5) **Live automation stays opt-in** after shipping: arming still needs the exact acknowledgement, the reviewed hash and a production qualification; nothing in 2.0 loosens a gate.
**Consequences.** New decisions carry the authorization scope in their inputs (new rationale hashes; old decisions are untouched). A rate-limited create call now pauses the account until the owner resolves it — the price of not resending into an undocumented ordering. Settlement can be *contested* on the first real resolution if the venue's `side` means the account's side; the hold is the intended way to find out. The RC label is the honest state: every mandatory owner check is enumerated, and the release is not "complete" while one is pending.

## ADR-037 — A position the app did not place is an external holding: listed, counted toward the limits, blocking entry on its contract — never a discrepancy, never a pause (2.0.0-rc.2)
**Context.** The first real-account view showed six `discrepancy` holds for positions the owner had placed by hand on the venue, on markets the app had never traded (`"intents":[]`). The 1.13 rule — "any venue position the app cannot account for pauses the account until a human explains it" — was written for markets where the app has orders; applied to hand-placed holdings it produced holds that could only be cleared by hand, never closed by themselves (four of the six markets had already settled), and paused an account the app had no stake in. The spec (RSK-06) asks for external holdings to count toward total/event limits conservatively and for opposing exposure or open orders on the same contract to block entry; it does not ask for a pause.
**Decision.** (1) A venue position on a market where the app has **no order of its own** is an *external holding*: reported by `positions()` with `external: true` and the venue's cost basis, shown in its own panel, never a discrepancy. (2) It counts toward the total, per-market and per-event limits at the venue's cost basis, or at $1 per contract when the venue reports none — the pilot limits describe the whole account. (3) It blocks app entry on that contract (`no_external_position`); other contracts are unaffected except through the caps. (4) Discrepancy holds remain exactly where they belong: markets with app orders whose fills plus known external orders do not add up to the venue position. (5) Legacy holds for hand-placed positions are resolved on the next reconcile with an explicit note and an audit event; their alerts close with them. (6) While adding (3) the on-contract gates were found to compare venue slugs with stored venue ids (RV-15) — the snapshot is now mapped to venue ids before any gate sees it. (7) Every hold and alert on the Trades page carries a plain-English meaning, the action expected of the owner, and a link into `docs/OPERATIONS_REFERENCE.md`.
**Consequences.** An account with large hand-placed holdings will see app decisions skip with `TOTAL_RISK_CAP_REACHED` until the owner raises the total-risk limit deliberately (which disarms) or the holdings settle — a visible, explained refusal instead of a hidden pause. The app still never touches, nets or settles a hand-placed position. Selling part of an *app* position on the website is unchanged: an external sell order on a contract with app orders, reconciled by action × side (RV-08), and a discrepancy only when the numbers still do not add up.

## ADR-038 — The reference lives in the app, the tutorial is derived from records, and the Arm blockers are the server's gates read back — the UI refresh changes how things are explained, never what they do (2.1.0)
**Context.** The owner's first look at a real account (2.0.0-rc.2) showed that the Trades page was correct and unreadable: six holds and two alerts with no plain-English path from "what is this" to "what do I do". The design handoff "UI refresh & integrated help" proposed a grouped sidebar, a `?` beside every term, a Learn panel and page, a six-step Guided start, and a Trades page that lists why *Arm* is unavailable — with the explicit constraint that terminology, page names, API contracts, business rules, privacy controls and confirmation flows stay as they are.
**Decision.** (1) **The reference text ships in the bundle** (`web/src/help/topics.ts`, 38 topics ported from the handoff and corrected against the code: reason codes, "Deadline reached", age-restricted videos) and is the primary source for the `?` popovers, the Learn panel and the Learn page; the GitHub copy is the secondary link on each topic, and `scripts/check-help-anchors.mjs` in `npm test` fails when a cited file or anchor is missing, so app and docs cannot drift. The text is static content: it never becomes an instruction to the model or the server. (2) **Nothing in the UI invents state.** The Guided start's six ticks are derived from `/api/settings`, `/api/videos`, `/api/predictions` and accepted links (one read-only route, `GET /api/market-links`, was added because the handoff's `/api/markets/links` did not exist); its only client state is `localStorage['pl.guidedStart']`. The Trades page's Arm blockers are the unmet `gates` and `dispatchBlockers` of `/api/trading/status`, the scheduler's reasons and the qualification report's status and `eventsNeeded` — rendered, not composed. Alerts are split by a fixed rule (discrepancy, unknown_submission, failed_cancel, stale_sync require the owner; the rest are informational) and every hold card is the topic's *what / app did / you do* plus the same resolution controls as before. (3) **Local-first stays local-first**: the design's Inter typeface is used only when installed (no web font), and the twelve Phosphor icons are inlined as SVG path data (MIT, attributed) rather than a runtime package or font, so the dashboard still fetches nothing on its own. (4) **The worked example is data, labelled synthetic**, rendered by one page and never written anywhere. (5) **Every pre-2.1 class name keeps rendering** through the new tokens, so components that were not redesigned (dossier, contract panel, market links, cards in Setup) look coherent without being rewritten.
**Consequences.** The dashboard has two workspace tests of its own (`npm test --workspace web`, run with tsx) and a docs-anchor check; a future topic must cite a real anchor. The visual verification in this release is a sandbox harness (compiled TSX against a mock API, Playwright at 1440 px and 390 px, 39 interaction checks); the Vite build and the run on real data remain owner steps and are listed as such in VERIFICATION.md. Nothing about the 2.0 release-candidate status changes: the owner evidence in SETUP §4.16 is still what stands between 2.0.0-rc.2 and 2.0.0.

*Round 2 (2.1.1).* The handoff's second round reordered what the first had built — verdict first with a "Read together" sentence, holds above the tiles with the owner's steps numbered, a strip instead of a Setup-only tutorial, one Escape order, viewport breakpoints — and asked one product question: does resolving a hold close its alert? The code said "only on two internal paths", so 2.1.1 makes it true on the owner's paths as well (`alertKeysForHold`), with regressions; Acknowledge still only hides a row. The other open items were answered from the code, not assumed: `dispatchBlockers` is `string[]`, `health.version` is read at process start, the verdict guard's rules are G1–G7. Everything else in round 2 stayed within the same rule: rendering existing responses, never inventing state.
